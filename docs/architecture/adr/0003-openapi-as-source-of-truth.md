# ADR-0003: OpenAPI як єдине джерело правди API

- **Номер:** 0003
- **Статус:** Accepted, 2026-11-27.
- **Компонент:** [[architecture/sdd#sdd-api|SDD: API]], [[api/index|API]]

## Контекст

У ЛР10 контракти API жили в трьох місцях одночасно: таблиця в README, SDD §5 і сам код. Краш-тест ЛР10 (коміт `ae1578c`) показав, що новий маршрут `GET /tasks/{task_id}` не потрапив у жоден документ, а тести цього не помітили.

## Розглянуті альтернативи

| Варіант | За | Проти |
|---|---|---|
| Code-first: `/openapi.json`, який генерує FastAPI | завжди збігається з кодом | контракт з'являється після коду, описи і приклади бідні, клієнти не можуть почати раніше |
| **API-first: `docs/api/openapi.yaml` у репозиторії (обрано)** | контракт рецензується до коду, Spectral, SDK і Swagger з одного файлу | файл може розійтися з кодом, тому потрібна перевірка дрейфу |
| Ручні таблиці в Markdown | просто | дублювання, немає валідації, немає генерації |

## Рішення

1. `docs/api/openapi.yaml` (OpenAPI 3.0.3, `info.version` за SemVer) є єдиним описом HTTP-контракту. Версію 3.1 відкинуто: openapi-generator 7.14.0 підтримує її як beta і в Python SDK втратив `null` у полях `due_date`, `owner_id`.
2. README і SDD не повторюють маршрути, а лише посилаються на нього.
3. Сторінка API рендериться з YAML через Swagger UI, SDK генерується з YAML.
4. Spectral (`.spectral.yaml`) перевіряє файл у CI.
5. `scripts/doc_audit.py` перевіряє, що кожен маршрут `tasks/api.py` є в YAML.
6. Дрейф проти запущеного API перевіряє Schemathesis.

## Наслідки

- **Плюси:** один файл для документації, Swagger UI, SDK і тестів контракту.
- **Мінуси:**
    - FastAPI теж генерує власний `/openapi.json`, тобто існують дві специфікації;
    - збіг між ними підтримується перевірками, а не автоматично;
    - знайдені розбіжності фіксуються як дефекти.
- **Коли переглянути:** якщо дрейф стане регулярним. Тоді варто генерувати моделі коду з YAML або навпаки.
