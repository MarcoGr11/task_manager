# RB-001: Відновлення JSON-сховищ з резервної копії

| Поле | Значення |
|---|---|
| Операція | відновлення `TASKS_DB`, `USERS_DB`, `CONSENTS_DB` з ланцюга «останній full + усі incr після нього» |
| Виконавець | SRE on-call (L2), див. [[maintenance-plan]] |
| Тривалість | виміряно 1349 мс від зупинки застосунку до `health 200` (drill 2026-11-27, 5 задач) |
| Втрата даних | усе, що записано після останнього бекапу (RPO, [[architecture/isd#isd-storage]]) |
| Каталог алертів | [[runbooks/index]] |
| Останній drill | 2026-11-27, вивід у `doc/lab12_results/restore_drill.txt` |

## Тригери

Кожен тригер відповідає алерту з каталогу. Правила лежать у `monitoring/alerts.yml`.

<a id="t1"></a>

- **T1.** Спрацював `TaskStoreReadErrors`: понад 5% запитів `/tasks*` повертають 5xx протягом 2 хв. Як вторинна ознака можливий `AvailabilityBudgetFastBurn`. Типова причина: `TASKS_DB` не читається, бо JSON пошкоджено або файл видалено.

<a id="t2"></a>

- **T2.** Спрацював `TaskStoreShrink`: `task_store_records` за 15 хв упав понад 10% або дорівнює `NaN` (сховище не читається). Це ознака втрати даних.

Якщо алерт є, але `GET /tasks` повертає 200, а JSON валідний, це не тригер RB-001. Тоді див. [[maintenance-plan#escalation]].

## Передумови

1. Є доступ до хоста, на якому працює API, і до каталогу бекапів `backups/`.
2. Активовано venv `.venv3.13`, поточний каталог `task_manager/`.
3. `BACKUP_PASSPHRASE` задано в оточенні. Ключ береться зі сховища секретів, ніколи з файлів.
4. Каталог бекапів містить повний архів, вік якого не перевищує 26 год (backup policy, [[architecture/isd#isd-backup]]).
5. Змінні `TASKS_DB`, `USERS_DB`, `CONSENTS_DB` збігаються з тими, з якими запущено API.
6. Інцидент заведено (SEV за [[maintenance-plan#escalation]]), час початку записано в UTC.

## Кроки

Команди виконано під час drill 2026-11-27, повний вивід у `doc/lab12_results/restore_drill.txt`. Порядок такий: спочатку дані, потім застосунок.

1. **Підтвердити тригер:**

    ```bash
    curl -s -o /dev/null -w '%{http_code}\n' localhost:8000/tasks
    curl -s localhost:8000/metrics | grep -E '^task_store_records'
    ```

    Очікується `500` і `task_store_records NaN`, або значення, менше за попереднє.

2. **Зупинити застосунок**, щоб припинити запис у сховище:

    ```bash
    kill $(lsof -tiTCP:8000 -sTCP:LISTEN)
    lsof -iTCP:8000 -sTCP:LISTEN || echo "port 8000 free"
    ```

3. **Зберегти пошкоджений стан** для розслідування:

    ```bash
    cp -p "$TASKS_DB" "$TASKS_DB.corrupt-$(date -u +%Y%m%dT%H%M%SZ)"
    ```

4. **Обрати і перевірити ланцюг бекапів:**

    ```bash
    ls -1 backups/
    python scripts/backup.py verify backups/<останній>-full.tar.gz.enc
    python scripts/backup.py verify backups/<кожен наступний>-incr.tar.gz.enc
    ```

    Кожен архів має дати `OK`. Якщо хоч один дає `FAIL`, ланцюг використовувати не можна: беремо попередній full і переходимо до ескалації.

5. **Відновити дані:**

    ```bash
    python scripts/backup.py restore backups/<full> backups/<incr1> backups/<incr2> ...
    ```

    Скрипт звіряє SHA-256 кожного файлу з маніфестом останнього архіву. Якщо хоч один хеш не збігся, скрипт не пише нічого і завершується з exit 1. Кожен файл замінюється атомарно через `os.replace`.

6. **Запустити застосунок і перевірити health:**

    ```bash
    uvicorn tasks.api:app --port 8000 &
    for i in $(seq 1 50); do curl -fsS localhost:8000/health && break; sleep 0.2; done
    ```

## Верифікація

| Перевірка | Команда | Очікування (drill 2026-11-27) |
|---|---|---|
| Health | `curl -s -o /dev/null -w '%{http_code}' localhost:8000/health` | `200` після 3 проб |
| Читання | `curl -s -o /dev/null -w '%{http_code}' localhost:8000/tasks` | `200` |
| Кількість записів | `curl -s localhost:8000/metrics \| grep ^task_store_records` | дорівнює `records` у маніфесті останнього архіву (8) |
| Алерти | Prometheus, вкладка Alerts | `TaskStoreReadErrors` і `TaskStoreShrink` стають inactive |

Записати в інцидент: час відновлення (UTC), архіви ланцюга і кількість втрачених записів (RPO).

## Відкат

Якщо верифікація не пройшла:

1. Знову зупинити API (крок 2).
2. Повернути збережений стан: `cp -p "$TASKS_DB.corrupt-<час>" "$TASKS_DB"`. Це повертає систему до стану перед відновленням, тобто нічого не втрачається.
3. Повторити кроки 4–6 з попереднім повним бекапом (старіший ланцюг) і записати збільшене вікно втрати.
4. Якщо й це не допомогло, ескалювати.

## Ескалація

| Умова | Кому | Канал |
|---|---|---|
| 15 хв без прогресу або `verify` дає FAIL на всіх ланцюгах | L3, розробник-власник модуля сховища (MarcoGr11) | за [[maintenance-plan#escalation]] |
| Втрата даних більша за RPO (1 год) або зачеплені `USERS_DB`, `CONSENTS_DB` (персональні дані) | продуктовий власник і відповідальний за захист даних | те саме; конкретні люди потребують підтвердження студента |

## Рівень автоматизації: 2 з 3

| Рівень | Що означає | Тут |
|---|---|---|
| 0 | ручні дії без інструкції | – |
| 1 | задокументовані команди, людина копіює їх | кроки 1–3 |
| **2** | скрипт виконує роботу, рішення приймає людина | `scripts/backup.py verify/restore`: перевірка хешів, атомарна заміна, відмова при неповному ланцюгу. Тести в `tests/test_backup.py` |
| 3 | автоматичне виявлення і виконання без людини | свідомо не впроваджено |

Чому не рівень 3. Відновлення завжди відкочує дані до моменту бекапу. Якщо алерт хибний, наприклад `TaskStoreShrink` спрацював через легітимне масове видалення, автоматичне відновлення саме знищить записи останньої години. Рішення «втратити дані за RPO» має ухвалювати людина.

Чому не рівень 1. Ручне `cp` з бекапу (процедура ЛР10, `docs/audit/restore_drill.txt`) не перевіряє цілісність і не захищає від неповного ланцюга. Це довів тест `test_restore_refuses_incomplete_chain`.
